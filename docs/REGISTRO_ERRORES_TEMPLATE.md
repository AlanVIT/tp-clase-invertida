# Registro de Errores — Operación Rescate II

Proyecto ejecutado con `npm install` + `npm run dev` y probado con `curl` (equivalente a Postman) sobre `http://localhost:3000`. Se detectaron 20 errores. Se listan en el orden en que conviene corregirlos (primero lo que bloquea todo el flujo, después seguridad, después lógica puntual, después detalles menores).

| N° | Archivo | Problema encontrado | Causa | Cómo lo detectaron | Solución aplicada |
|----|---------|----------------------|-------|---------------------|--------------------|
| 1 | `src/app.js` | `req.body` llegaba `undefined` en **todas** las rutas POST/PUT. | Nunca se registró el middleware `express.json()`, así que Express no parseaba el body JSON de la petición. | `POST /api/loginn/register` con body JSON devolvía `500` con el mensaje *"Cannot destructure property 'name' of 'req.body' as it is undefined"*. | Se agregó `app.use(express.json());` antes de montar las rutas. |
| 2 | `src/app.js` | Las rutas de autenticación no eran alcanzables en ninguna URL razonable. | Typo: `app.use("/api/loginn", authRoutes)` (sobraba una "n"), en vez de un prefijo semántico como `/api/auth`. | Ningún cliente podía adivinar `/api/loginn/register`; probar `/api/auth/register` daba `404 Cannot POST`. | Se cambió el prefijo a `app.use("/api/auth", authRoutes)`. |
| 3 | `src/app.js` | Las rutas de administración compartían prefijo con las rutas de usuario (`/api/users`), mezclando dos dominios distintos. | Copy/paste del mismo path (`"/api/users"`) al montar `adminRoutes`. | Lectura del archivo: `adminRoutes` quedaba expuesto en `/api/users/all`, sin relación clara con "admin". | Se montó `adminRoutes` en su propio prefijo: `app.use("/api/admin", adminRoutes)`. |
| 4 | `src/utils/token.js` | `signToken` era `undefined` al importarlo, y **registro/login rompían siempre** al intentar firmar un token. | Typo: `module.export = {...}` (sin la "s" final). Node expone el módulo a través de `module.exports`; asignar `module.export` crea una propiedad que Node ignora, por lo que `require("../utils/token")` devolvía `{}`. | `const { signToken } = require(...)` quedaba `undefined`; al llamar `signToken(user)` en el controller se rompía con *"signToken is not a function"*. | Se corrigió a `module.exports = { signToken }`. |
| 5 | `src/utils/token.js` | El token nunca se firmaba con el secreto real del proyecto (`.env`). | Typo: `process.env.JWT_SECRETT` (con doble T) en vez de `JWT_SECRET`. Al no existir esa variable, siempre caía en el valor por defecto hardcodeado `"super-secret"`. | Se comparó el nombre de la variable contra `.env` (`JWT_SECRET=super-secret`) y se confirmó que por casualidad el valor por defecto coincidía, pero cualquier cambio futuro del secreto en `.env` no tendría efecto real. | Se corrigió a `process.env.JWT_SECRET`, sin fallback hardcodeado (el secreto debe salir siempre de la config). |
| 6 | `src/utils/token.js` | Los tokens expiraban a los **2 segundos** de emitidos. | `expiresIn: "2s"` — valor de expiración absurdamente corto, probablemente un error de tipeo por `"2h"`. | Se generó un token, se esperó unos segundos y se probó contra una ruta protegida: el token válido era rechazado casi de inmediato. | Se cambió a `expiresIn: "2h"`, un valor razonable para sesiones de prueba. |
| 7 | `src/utils/token.js` | El payload del token solo incluía `role`, nunca el `id` del usuario. | `jwt.sign({ role: user.role }, ...)` — faltaba incluir `id`. | `req.user.id` daba `undefined` en todos los controllers que dependían de él (`getProfile`, `updateMe`), aun después de arreglar la verificación del token. | Se agregó `id: user.id` al payload: `jwt.sign({ id: user.id, role: user.role }, ...)`. |
| 8 | `src/middleware/authMiddleware.js` | **Vulnerabilidad crítica**: cualquiera podía forjar un token con cualquier `role` (por ejemplo `"admin"`) sin conocer el secreto, y el middleware lo aceptaba igual. | Se usaba `jwt.decode(token)`, que solo decodifica el payload en base64 **sin verificar la firma**, en vez de `jwt.verify(token, secret)`. | Se construyó a mano un JWT con firma inventada (`payload: {id:"1", role:"admin"}`, firma `"firmainventada"`) y se envió contra una ruta protegida: fue aceptado como válido (el único motivo por el que fallaba después era el bug #1, no la seguridad). | Se reemplazó por `jwt.verify(token, process.env.JWT_SECRET)` dentro de un `try/catch`, rechazando con `403` cualquier token cuya firma no sea válida. |
| 9 | `src/middleware/authMiddleware.js` | Las rutas "protegidas" eran accesibles **sin ningún token**: si no había token, se dejaba pasar como usuario `"guest"` en vez de rechazar. | Condición `if (!token || decoded) { ... next() }`: la ausencia de token (`!token`) también dejaba pasar la request. | `GET /api/users/orders` sin header `Authorization` devolvía `200 OK` con datos, en vez de rechazar el acceso. | Se reescribió la lógica: si no hay token se responde `401 Token requerido` de inmediato; solo se llama a `next()` si `jwt.verify` tiene éxito. |
| 10 | `src/routes/adminRoutes.js` | La ruta `GET /all` (listado de todos los usuarios, incluyendo hash de contraseña) no tenía **ninguna** protección: ni autenticación ni verificación de rol. | El router solo registraba `router.get("/all", listUsers)`, sin `authMiddleware` ni chequeo de rol. | `GET /api/users/all` sin header `Authorization` devolvía `200 OK` con la lista completa de usuarios y sus hashes bcrypt. | Se agregó `authMiddleware` y un middleware `requireAdmin` (verifica `req.user.role === "admin"`) antes de `listUsers`. Ahora responde `401` sin token y `403` si el usuario autenticado no es admin. |
| 11 | `src/controllers/authController.js` (`register`) | Cuando faltaban datos (`name`/`email`/`password`), se respondía `400` pero la función seguía ejecutándose. | Faltaba la palabra clave `return` antes de `res.status(400).json(...)`. | Con body incompleto, la respuesta llegaba igual, pero el código intentaba seguir procesando (riesgo de "headers already sent" si más adelante se agregara otra lógica). | Se agregó `return` antes del `res.status(400)...`. |
| 12 | `src/controllers/authController.js` (`login`) | Si el email no existía, se enviaba una respuesta pero el código seguía ejecutando y **crasheaba** al intentar leer `user.password` de `undefined`. | Faltaba `return` después de `res.status(200).json({ message: "Credenciales invalidas" })` (nota: además el status estaba mal, ver ítem #14). | `POST /api/auth/login` con un email inexistente devolvía `500` con *"Cannot read properties of undefined (reading 'password')"*. | Se agregó `return res.status(401).json(...)` cortando la ejecución inmediatamente. |
| 13 | `src/controllers/authController.js` (`login`) | El login **nunca** validaba correctamente la contraseña, ni siquiera con la contraseña correcta. | `bcrypt.compare(user.password, password)` tenía los argumentos invertidos: el primer argumento debe ser el texto plano y el segundo el hash. ## Cómo se validó cada corrección

Se levantó el servidor (`node src/server.js`) y se probó cada endpoint con `curl`, simulando lo que se haría con Postman:

- **Registro**: `POST /api/auth/register` con datos completos → `201` y token; con datos incompletos → `400` y corta ejecución; con email repetido → `409`; ninguna respuesta incluye el hash de password.
- **Login**: con password correcta → `200` y token; con password incorrecta → `401`; con usuario inexistente → `401`; ninguna respuesta incluye el hash de password.
- **Rutas protegidas** (`GET/PUT /api/users/me`, `GET /api/users/orders`): sin token → `401`; con token válido → `200` con los datos del usuario autenticado (nunca de otro); con un JWT de firma inventada (bien formado pero no firmado con el secreto real) → `403`; con token expirado → `403`.
- **IDOR**: un usuario normal autenticado que intenta pisar el perfil de otro (`userId` distinto en el body de `PUT /me`) solo puede modificar su propio perfil.
- **Rutas de administrador** (`GET /api/admin/all`): sin token → `401`; con token de un usuario `role: "user"` → `403`; con token de un usuario `role: "admin"` → `200` con la lista completa de usuarios, sin exponer los hashes de password.

Todos los casos fueron ejecutados contra el servidor real (`npm run dev` / `node src/server.js`) en `http://localhost:3000`, no simulados.
